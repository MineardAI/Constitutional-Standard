# Release Continuity and Compatibility Realization Profile

Constitutional source: `IMP-008_Implementation_Release_Continuity_and_Compatibility_v0.2.0_Candidate_Review_Draft.md` (Candidate Review Draft; status preserved).

Ownership: dedicated `constitutional-release` crate. It realizes released implementations, release identities and manifests, release packages, lineage, contextual compatibility claims and assessments, change effects, migration requirements/plans/records, evidence applicability, and assurance applicability.

Canonical surfaces use the existing IMP-005 `CanonicalObject` architecture. Validation is deterministic and typed. Evidence, verification, assurance, and traceability remain references owned by their respective components.

The implementation does not publish packages, execute migrations, activate implementations, perform deployment, establish authority, determine conformance, certify, or create operational recognition. Version ordering is not constitutional precedence; publication is not activation; compatibility is not correctness, assurance, conformance, or authority.

Second closure remediation adds deterministic migration-cycle and supersession-graph checks, release-history continuity, cross-assessment compatibility contradiction detection, subject-bound release traceability, and bounded activation/recognition reference validation. Activation semantics remain owned by `constitutional-activation`; release traceability does not grant activation or recognition.

Contract-derived remediation adds explicit successor evidence/assurance/migration applicability and preserved predecessor resolution, plus typed authority/baseline/scope context on the release-to-operational boundary. No graph acyclicity or automatic applicability inheritance is required, and release still does not activate or deploy an implementation.
